# GS1 DataMatrix generation (`symbol` package)

> Prototype for [#24](https://github.com/galenzo17/gs1-go/issues/24). Barcode
> generation is out of scope under [ADR 0002](adr/0002-parser-scope.md); this
> package exists to discuss whether that should change. It stays in a fork
> branch until the maintainer decides.

The `symbol` package renders GS1 element strings as ECC 200 Data Matrix
symbols (ISO/IEC 16022). Like the rest of the module it depends only on the
Go standard library.

## Usage

```go
import "github.com/galenzo17/gs1-go/symbol"

m, err := symbol.GS1DataMatrix("(01)04150000021126(17)250630(10)ABC123", symbol.DataMatrixOptions{})
if err != nil {
    return err
}
m.Rows, m.Cols         // 20 20
m.Dark(0, 0)           // true: module grid, no quiet zone
svg := m.SVG(10, 1)    // 10 px per module, 1 module quiet zone
err = m.PNG(w, 10, 1)  // 8-bit grayscale PNG
img := m.Image(10, 1)  // *image.Gray for your own pipeline
```

The input is anything `gs1.Parse` accepts: bracket notation, raw element
strings with ASCII 29 as FNC1, or AIM-prefixed scanner output. It is parsed
first, so invalid element strings fail before any symbol is built.

### Choosing an output

| Output | Use it for | Notes |
|---|---|---|
| `SVG(scale, quiet)` | print pipelines, web | One path, one subpath per run of dark modules. Two allocations per call. |
| `PNG(w, scale, quiet)` | general purpose raster | 8-bit gray. Encoder buffers are pooled across calls. |
| `png.Encode(w, m.Paletted(scale, quiet))` | smallest files | 1-bit palette: about half the size of `PNG`, a little faster on small symbols, about 14% slower on very large images. |
| `Image` / `Paletted` | compositing into labels | Standard `image.Image` values. |

`scale` is pixels per module and should match the printer's X-dimension.
The quiet zone is in modules; GS1 asks for at least one.

### Repeated encoding: `Encoder`

The package-level functions keep no state. The layout of the modules
depends only on the symbol size, never on the data, so a program that
encodes many symbols can keep an `Encoder`, which caches each size's layout
after first use:

```go
var enc symbol.Encoder // zero value is ready; safe for concurrent use
for _, s := range scans {
    m, err := enc.GS1DataMatrix(s, symbol.DataMatrixOptions{})
    ...
}
```

A cached layout costs two bytes per module: about 41 KiB for 144x144, 220
KiB if all 30 sizes are used. It lives as long as the `Encoder` does.
Output is identical to the package functions. See
[performance.md](performance.md) for when this pays off.

### Rectangular symbols

`DataMatrixOptions{Rectangular: true}` picks the smallest of the six ECC 200
rectangular sizes (8x18 to 16x48, up to 49 data codewords). Data that does
not fit returns `ErrDataTooLong`.

### Command line

```bash
gs1 datamatrix "(01)04150000021126(17)250630(10)ABC123" > dm.svg
gs1 datamatrix -o dm.png -scale 8 -quiet 2 "(01)04150000021126(10)LOT42"
gs1 datamatrix -rect -o dm.svg "(01)04150000021126"
```

## What is implemented

- All 24 square and 6 rectangular ECC 200 sizes, 10x10 to 144x144.
- GS1 mode: FNC1 in first position, FNC1 as separator after
  variable-length fields that are not last.
- ASCII encodation with digit-pair compaction.
- Reed-Solomon over GF(256) (polynomial 0x12D), block interleaving, and the
  144x144 ECC layout that deployed readers expect (see below).
- Annex F module placement with the four corner patterns and the fixed
  pattern for sizes whose data area is not a multiple of 8 bits.

## Not implemented (yet)

- C40, Text, X12, EDIFACT and Base 256 encodation. ASCII is valid for every
  GS1 element string, but some inputs pick a larger symbol than an
  optimizing encoder would.
- DMRE sizes (ISO/IEC 21471).
- Element string ordering. The package keeps the order it is given and only
  inserts FNC1 where needed; `gs1.Encode` (#16, PR #34) should replace the
  internal `elementString` once it lands.
- GS1-128, GS1 QR, EAN/UPC, ITF-14 and ZPL output from #24.

## 144x144 ECC layout

144x144 is the only size whose data codewords do not split evenly over its
Reed-Solomon blocks (eight blocks of 156, two of 155). Read literally,
ISO/IEC 16022 places ECC codeword j of block b at `DataCW + j*Blocks + b`.
zxing, libdmtx, BWIPP and zint all put the ECC of the two short blocks
first instead, and readers reject the literal layout. The package follows
the deployed readers: see `dmECCPos` and
[zxing-cpp#259](https://github.com/zxing-cpp/zxing-cpp/issues/259).

## Verification

| Check | What it proves | Where |
|---|---|---|
| zint golden, `TestDataMatrixGolden` | every size (forced) and two GS1 symbols match zint 2.16 module for module, for the package functions and for `Encoder` | `symbol/testdata/datamatrix-golden.txt`, regenerated by `gen-golden.sh` |
| Independent decoder | 26 symbols from 8x32 to 144x144, square and rectangular, decode with zxing-cpp as `]d2` back to the original element string | `symbol/testdata/verify-decode.sh` (needs `uv`, runs outside `go.mod`) |
| ISO annex vector | `123456` gives ECC `114 25 5 88 102` | `TestDMECCGoldenVector` |
| Syndromes | every RS block of every size has zero syndromes | `TestDMECCSyndromes` |
| Placement coverage | every mapping module is written exactly once, every codeword consumed | `TestDMPlaceCoverage` |
| Race | concurrent `Encoder` first use and pooled PNG buffers | `go test -race` |

zint and zxing-cpp are only needed to regenerate or re-verify; `go test`
needs nothing outside the standard library.

```bash
go test ./symbol/
bash symbol/testdata/verify-decode.sh     # needs uv
bash symbol/testdata/gen-golden.sh        # needs zint, only to refresh goldens
```
